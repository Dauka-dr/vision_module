# Распознавание действий людей по видео

Определяет для каждого человека в кадре, что он делает: смотрит в телефон,
пишет, спит, дерётся и ещё семь классов. Работает с десятками людей
одновременно — проверено на 86.

```
кадр
 └─ RTMDet ──────── люди + объекты (телефон, книга, ноутбук) за один проход
     ├─ RTMPose ─── скелет каждого, 17 точек COCO, батчем
     ├─ трекер ──── стабильный ID, буфер из 100 поз
     ├─ ST-GCN++ ── действие по буферу (человек + ближайший сосед)
     ├─ правила ─── поза по геометрии головы и корпуса
     └─ арбитраж ── объект у рук решает спор «телефон vs пишет»
```

## Быстрый старт

```powershell
git clone <репозиторий> && cd <репозиторий>
.\install.ps1              # окружение: conda, torch, OpenMMLab
python fetch_assets.py     # веса моделей и тестовая сцена (~150 МБ)
python demo.py             # веб-камера
```

Проверить, всё ли на месте: `python fetch_assets.py --check`

```powershell
python demo.py --source video.mp4 --save out.mp4
python demo.py --source photo.jpg
python demo.py --no-action                # только позы, без загрузки модели
```

В окне: у каждого свой цвет, `#ID`, скелет и подпись. Выход — `q`.

## Что распознаётся

Одиннадцать классов из двух разных источников, и это не деталь реализации, а
суть задачи: **действия** имеют временную сигнатуру и распознаются нейросетью,
**состояния** — удерживаемые позы, которых нет ни в одном публичном датасете, и
они выводятся из геометрии скелета.

| действия (ST-GCN++, обучена) | состояния (правила) |
|---|---|
| смотрит в телефон | сидит |
| пишет / работает с ноутбуком | стоит |
| поднимает руку | сидит, внимателен |
| разговаривает с соседом | спит / голова на парте |
| идёт | |
| бежит | |
| дерётся | |

NTU RGB+D — единственный скелетный датасет с предобученными весами — целиком
состоит из **действий-переходов** («сесть», «встать»). Удерживаемых состояний в
нём нет ни в версии на 60 классов, ни на 120, поэтому научить им модель оттуда
нельзя при любом количестве примеров.

## Точность

**97.0%** на отложенной выборке NTU при рабочих настройках (буфер 100 кадров,
порог 0.6). Замеры: [metrics/](metrics/).

Три решения, каждое из которых стоит процентов:

**Длина буфера.** Модель обучена на клипах в 100 кадров. Короткий буфер экономит
время до первого ответа, но заметно теряет в точности:

| буфер | точность | ждать при 3 к/с |
|---|---|---|
| 30 кадров | 87.0% | 10 с |
| 60 кадров | 93.2% | 20 с |
| **100 кадров** | **97.0%** | **33 с** |

**Парная подача.** Три класса — `дерётся`, `разговаривает`, `идёт` — в NTU сняты
как взаимодействия двух человек, и модель обучена видеть оба скелета. Подача
одиночки даёт 85% вместо 99%, поэтому каждый классифицируется вместе с ближайшим
соседом.

**Арбитраж объектами.** «Телефон» и «пишет» дают одинаковую позу — голова вниз,
руки вперёд. На отложенной выборке эта пара составила **87% всех ошибок модели**.
Различает только предмет в руках, поэтому найденный объект переопределяет ответ
сети. Свидетельство одностороннее: найденный телефон — сильный довод,
ненайденный — не довод, потому что объектный поток покрывает лишь треть людей.

## Как библиотека

```python
from recognizer import Recognizer

rec = Recognizer(scene='auto')
for frame in video:
    for p in rec.process(frame):
        print(p.who, p.label_ru, p.action_conf, p.objects)
```

Поля: `state` (есть всегда), `action` (когда буфер полон), `objects`,
`identity` (если подключена внешняя модель), `label` — один ответ для показа.

## Подключение распознавания личности

Ключ соединения — `track_id`: личность определяется **один раз на трек**, а не
на каждом кадре, поэтому внешняя модель запускается несколько раз за сессию.

```python
from identity import FaceCropAdapter
rec = Recognizer(identity_provider=FaceCropAdapter(my_model))
```

Адаптеры под три интерфейса: кроп лица, кроп фигуры (ReID), целый кадр.

Дальность считается заранее: `python metrics/face_budget.py`. При 70° и пороге
30 px 4K достаёт **5.8 м** — первые 2–3 ряда. Дальние ряды не распознаются ни при
каком разумном сенсоре, поэтому `identity` всегда nullable и система работает без
имени.


## Требования

GPU с 4+ ГБ (проверено на RTX 4050, 6 ГБ). Версии закреплены намеренно —
экосистема OpenMMLab не обновлялась с 2023–24:

| пакет | версия | почему |
|---|---|---|
| PyTorch | 2.1.0+cu121 | последняя с готовыми Windows-wheel для mmcv |
| mmcv | 2.1.0 | mmdet 3.3.0 жёстко требует `<2.2.0` |
| numpy | 1.26.4 | стек собран под 1.x, с 2.x падает |
| opencv-python | 4.9.0.80 | 5.x требует numpy≥2 — конфликт |

`pip install -r requirements.txt` одной командой **не сработает**: torch и mmcv
идут с отдельных индексов. Используйте `install.ps1` или шаги из комментариев в
`requirements.txt`.

## Ограничения

**97% — это на NTU, а не на вашей аудитории.** Там актёры выполняют действия
подчёркнуто, по одному, в пустой комнате, лицом к камере. В лекционном зале и
телефон, и тетрадь выглядят как «голова опущена, руки на парте», человек снят
сверху и наполовину закрыт партой и соседом. Реальная точность будет заметно
ниже, и настоящую цифру даст только съёмка на месте.

**Действия требуют видео.** На одном фото предсказываются только позы: действие
определяется движением, которого в статичном кадре нет.

**Правила для поз откалиброваны на одной сцене.** Пороги в `states.py` подобраны
по одной фотографии и одному ракурсу — самая требующая проверки часть.

**Ноги почти не видны.** В аудитории бедро и колено с одной стороны видны у 11%
людей: парты закрывают всё ниже пояса. Поэтому «сидит/стоит» определяется по
голове и пропорциям корпуса. Ограничение в данных, а не в методе — нейросеть
столкнулась бы с тем же.

**«Внимателен» — размытая метка.** Не физическое свойство, а остаточный класс
«сидит и больше ничего не обнаружено».

**Скорость.** На RTX 4050 полный кадр аудитории идёт на 2–4 кадра/с.
